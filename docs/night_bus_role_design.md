# 晚安车升级设计:车主/乘客角色 + 选车 + 意向树种

> 状态:**已实现**（代码落地于 main.py / database.py / _conf_schema.json）
> 决策汇总:
> - 车主名额**不限制**
> - 树种**宽松匹配**(AI 尽量匹配图库,匹配不到接受自由文本)
> - 无车主时发车**照发 + 提示缺司机**
> - 没指定车主的乘客 → **独立待定池**
> - 车主取消后 → 乘客**自动落回待定池**
> - 一人一晚**只能一个身份**(车主 或 乘客,不能同时)
> - 车主到点提醒:**意向时间优先**,没填的按统一发车时间;**仅群里 @车主**;内容**带乘客名单**
> - 报名提示教程:**每日每群首次报名附带**精简版;未指定身份时**默认乘客**并提示可改当车主

## 一、目标

1. 报名晚安车时声明自己的身份:**车主**(司机)或**乘客**
2. **乘客可选择已报名的车主的车**(多辆车并行,乘客挑车坐)
3. 报名时填写**意向树种**(已有 `preferred_tree` 基础,升级为 AI 匹配图库 + 分区展示)

## 二、现状基础

- 报名表 `night_bus_signups` 已含 `preferred_time`、`preferred_tree`(自由文本)
- 4 个 AI 工具:`signup_night_bus` / `cancel_night_bus` / `query_night_bus_signups` / `get_user_night_bus_count`
- 发车通知文案已有"请司机和各位乘客准备",但**无真实角色字段**
- 树种图库:`tree/tree_names.json`(164 个),已有 `search_tree_by_name` 工具可复用

## 三、数据模型变更

`night_bus_signups` 表新增两列:

| 列 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `role` | TEXT | `'passenger'` | `'driver'`=车主 / `'passenger'`=乘客 |
| `driver_id` | TEXT | NULL | 乘客所乘车主的 `user_id`;车主本人为空;未选车主(待定)也为空 |

**"一辆车"的唯一标识** = `(driver_id, group_id, signup_date)`,即一个车主一晚开一辆车。不需要新建表,一个外键列即可。

- 迁移方式与现有 `preferred_time` 一致:`ALTER TABLE ... ADD COLUMN`,已存在则跳过
- 旧记录自动归为 `passenger`、`driver_id=NULL`,无需数据清洗
- `preferred_tree` 保留,存中文树种名(尽量对齐 `tree_names.json`)

## 四、规则设计(已定)

| 规则 | 设计 |
|---|---|
| 车主名额 | **不限制**,谁都能报车主(开自己的车) |
| 选车 | 乘客可指定坐某位已报名车主的车;未指定则进**待定池** |
| 待定池 | 独立分区展示,不自动分配,司机可自行拉人 |
| 车主取消 | 该车主车上的乘客**自动落回待定池**(重新分区展示) |
| 双重身份 | **禁止**:一晚只能一个身份。已是车主的不能再作为乘客坐别人的车(反之亦然) |
| 重复报名 | upsert 更新角色/时间/树种/所乘车(换角色或换车=重新报名) |
| 取消报名 | 删除当日记录;若为车主,其乘客落回待定池 |
| 树种校验 | **宽松匹配**:AI 尽量用 `search_tree_by_name` 匹配真实树种,匹配不到也接受自由文本,报名不卡壳 |
| 发车条件 | 沿用"报名人数 > 2";无车主也照发,末尾附加缺司机提示 |

## 五、消息格式

> **格式铁律:名单一律"每行一人、带编号",严禁用 `、` 拼接在一行。**
> 原因:群昵称可能很长,并排拼接会导致乘客名字挤成一团看不清。
> 每行格式:`  {序号}. {名字}({身份},{时间},{树种})`,无信息的部分省略,如 `1. 小红(蓝花楹)`。

### 车主到点提醒(新增)

**触发时机**(意向时间优先):
- 车主报名时填了意向时间(如"11点")→ 到意向时间提醒
- 没填意向时间 → 按统一发车时间(`night_bus_notify_time`,默认 22:00)提醒

**推送方式**:仅**群里 @车主**(不用私聊),每个车主单独一条群消息 @他本人

**提醒内容**(带乘客名单):

```
⏰ 到点啦!小明,你的晚安车该发车了~

🚗 你的车(2人):
  1. 小明(车主,11点,樱花)
  2. 小红(蓝花楹)

请打开 Forest 创建房间,把邀请发到群里,我会自动提取密钥!
```

- 无乘客时:
```
⏰ 到点啦!小明,你的晚安车该发车了~

目前还没有乘客,记得邀请大家上车~
```

**去重**:每天每车只提醒一次(记录已提醒状态,定时任务每分钟检查时不重复推送)

**技术要点**:
- 群里 @需要构造带 At 组件的消息链,不能用纯 Plain 文本
- 需要新增一个"按意向时间到点提醒"的定时检查逻辑(不同于现有整点检查):
  - 现有 `_schedule_loop` 按固定时间(如 22:00)整点比对
  - 意向时间是自由文本("11点"/"10点半"/"10点30分"),需解析成分钟数,逐分钟比对
- 提醒记录需持久化(数据库表或字段),避免重启后重复提醒

### 报名提示教程(新增)

**目的**:防止新用户不会用,报名时给简单教程。

**触发时机**(已定):**每日每个群首次报名成功时附带**教程;当天同群后续报名不再重复。

**教程内容**(精简版 4-5 行):

```
🚌 晚安车小贴士:
• 当车主:说"我当车主,11点,樱花"
• 当乘客:说"我坐小明的车"或"我当乘客"
• 取消:说"取消晚安车"
• 报名时间:18:00-24:00,发车时间车主自定(如"11点")
```

**默认身份提示**(已定):用户报名时没说自己当车主/乘客 → 默认按**乘客**报名进待定池,并在回复里附带提示:

```
(提示)你已按乘客报名。想当车主请说:我当车主
```

**技术要点**:
- 教程附带状态需按 `(group_id, signup_date)` 记录,当天同群只附一次(可复用/仿照去重机制)
- 教程文案做成配置项,方便管理员改

## 六、AI 工具改造

### `signup_night_bus` 新增参数

| 参数 | 说明 | 示例提取 |
|---|---|---|
| `role` | 身份:`车主`/`乘客` | "我当车主/司机/开车" → `车主`;"我当乘客/坐车" → `乘客` |
| `join_driver` | 乘客要坐的车主(名字/昵称) | "我坐小明的车" → `小明` |
| `preferred_time` | 意向时间(已有) | "11点" |
| `preferred_tree` | 意向树种(已有) | "樱花" |

- 未提及 role → 默认 `passenger`(进待定池),并在回复中附带提示:"你已按乘客报名。想当车主请说:我当车主"
- 未提及 join_driver → 进待定池
- **选车校验**:join_driver 必须在当前报名车主的列表中,否则拒绝并列出当前可用车主
- **双重身份校验**:若用户已是车主,拒绝再以乘客身份坐别人的车(反之亦然)

### 系统提示词扩展示例

- "晚安车11点,我当车主,种樱花" → `signup_night_bus(preferred_time="11点", role="车主", preferred_tree="樱花")`
- "我坐小明的车,蓝花楹" → `signup_night_bus(role="乘客", join_driver="小明", preferred_tree="蓝花楹")`
- "报名晚安车" → `signup_night_bus(role="乘客")`(进待定池)

### 角色/选车关键词(提示词给 AI)

- 车主同义词:车主、司机、开车、驾驶、开车的
- 乘客同义词:乘客、坐车、搭车、乘车
- 选车表达:坐X的车、上X的车、跟X、X的车

### 解析机制:AI 理解 + 代码校验(分层架构)

**核心原则:语义解析交给 AI,校验/匹配/落库交给代码。不硬编码关键词列表,也不让 AI 判断对错。**

| 层级 | 用什么 | 处理什么 |
|---|---|---|
| **语义理解** | **AI**(tool_loop_agent) | 从自然语言提取 `role`(车主/乘客)、`join_driver`(坐谁的车)、`preferred_time`、`preferred_tree` |
| **校验与落库** | **硬编码**(代码逻辑) | 选的车主是否存在、双重身份冲突、报名时间窗口、写库、查重、去重 |

**为什么语义用 AI、不用硬编码关键词:**

1. 人类语言太灵活,同义表达无数种:
   - 车主:"我当司机""我来开车""我开一辆""我当车主"
   - 选车:"我坐小明的车""我跟小明""我想上小明的车""小明那辆带我一个"
   - 硬编码关键词列表永远列不全,还容易误伤(如"小明开车去上班"这类无关话)
2. 单字关键词(如"车")极易误匹配,语义提取是 LLM 擅长的事
3. 现状已经这么干:`preferred_time`/`preferred_tree` 就是 LLM 提取的,效果已验证

**关键点:`join_driver` 选车,AI 只负责"提名",代码负责"找人":**

```
用户说"我坐小明的车"
    ↓ AI 提取
join_driver = "小明"   ← 用户口中的昵称,可能是"小明"也可能是"阿明"或QQ名
    ↓ 代码层(硬编码逻辑)
在今日车主列表里模糊匹配 "小明" → 找到 user_id
    ↓ 匹配不到?
拒绝 + 列出当前可用车主名单,让用户重新选
```

这一步**必须代码做**,不能靠 AI 猜——因为车主名单是动态的、来自数据库,AI 不知道当前谁报名了车主。

**完整流程图:**

```
用户消息 → 触发关键词/@机器人
    ↓
LLM 分析语义 → 决定调用 signup_night_bus(role="乘客", join_driver="小明", preferred_tree="樱花")
    ↓
工具代码:校验报名时间 → 校验双重身份 → 校验 join_driver 是否在今日车主列表(模糊匹配)
    ↓
落库 → 生成报名成功消息(按车分组) → 每日首次附带教程 → 发到群里
```

**模糊匹配策略(代码层):**
- 精确匹配用户昵称 → 匹配上直接用
- 精确失败 → 包含/被包含匹配 → 仍失败 → 拒绝并列出候选车主
- 多个候选时提示用户补充信息(如 QQ 号尾号)
